## 根因与修复边界

已证实的应用缺陷：原引擎将每个已播放句子保存为单独的普通文本 assistant 历史，服务端又原样发回要求 JSON 的模型。第二轮开始，历史示例与输出格式约定不一致，还出现相邻 assistant 消息。系统提示始终存在，`thinking.type=disabled`、`response_format=json_object` 和 `max_tokens=650` 各轮一致。单纯扩大解析容错不可能把全空白回复变成有效对白。

现在每轮只保存一条完整 JSON assistant 历史，累计已完成呈现的对白和当时已校验指令；未听完/未呈现的部分不保存。用户轮次与首个完成句子一起提交到历史，失败或快速打断不会留下虚构的已完成交换，手动重试也不重复加入失败输入。服务端兼容旧页的普通文本历史，合并相邻同角色消息；损坏 JSON/未知指令不会被截成对白。历史仍有原有数量和长度上限。

修前真实复现及修后同话题连测支持上述定位；没有取得云端模型内部推理，不能宣称数学上证明每次空白都由这个因素单独造成。DeepSeek 官方也说明 JSON 模式偶尔可能返回空内容，不能保证零故障。真实空白仍清楚报错，不伪造回复、不自动二次收费。

诊断新增 trim 后长度、历史条数、assistant 数和消息数；最近 20 次成功/异常均只存枚举、数字和布尔值，另保留最近异常。没有原始对白、系统提示、密钥、请求头、原始错误或会话 ID，位于忽略的 `.local/` 中。
